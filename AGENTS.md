# Codex Window Primer agent rules

- This repository is public source. Never add `auth.json.enc`, OAuth tokens, refresh tokens, account identifiers, or an age private key.
- A user must copy the template into a separate Private runtime repository before adding credentials.
- For natural-language schedule requests in a deployed private copy, Codex directly updates `schedule.json` and all marked workflow cron entries together; do not ask the user to hand-edit schedule JSON, workflow YAML, cron, or UTC values.
- Prefer v2 `weekly` and `dates` rules: `override` replaces, `extra` appends, and `cancel` limits its effect to the stated slot/date. Interpret “改成” as replacement and “再加一个/还要/也开工” as addition.
- For every date-rule edit, first read that date's current effective slots, apply only the requested add/remove/replace operation, and then choose the smallest lossless rule representation. If mixed history cannot be represented by one `extra` or `cancel`, normalize the complete result to `override`; never let a later edit restore or discard an earlier confirmed change.
- For an explicit dated or temporary work request, compare each targeted slot's actual prime instant with the current instant (use `targeted_prime_action(plan, now, target_date=..., targeted_slots=...)` and `cron_entries(plan, now=...)`). The work date and prime date may differ when a slot crosses midnight. If the target prime is at least 10 minutes in the future, generate the dated cron normally. If it has passed or is less than 10 minutes away and the wording clearly means the work still happens, save the dated plan without that near-term/expired date cron and invoke the existing `workflow_dispatch` once. Explain that this is best-effort: a new window starts with the request only when no five-hour window is active; an active window is not reset, so the original reset target is not guaranteed. With multiple targeted slots, dispatch once for the missed target while retaining cron entries for future targets. A canceled target never dispatches, and an unrelated recurring slot must not suppress the targeted decision. `today_prime_action(plan, now, targeted_slots=...)` is only the backward-compatible same-calendar-date wrapper. Never add a new workflow or polling loop.
- An enabled v2 plan containing recurring weekly slots must have `active_from_local`; when creating one, set it to the current local date in the plan timezone. The disabled public template may keep it null. Use the same bounded active-from projection for cron generation and collision checks.
- `active_from_local` and `active_until_local` limit only the recurring weekly base. Explicit `dates` rules are concrete-date exceptions: `override` and `extra` remain effective outside the active range, while `cancel` has no effect without a weekly occurrence. Effective slots, cron generation, due gating, targeted actions, and collision detection must use this same rule.
- Before committing a schedule change, run `find_collisions(plan)`. Group exact prime instants first: identical instants share one window and are not collisions. For every distinct adjacent prime gap below `window_duration_minutes`, tell the user which slots and local prime times conflict, then ask which target to keep or explicitly mark the affected target as best-effort; never claim both reset targets are independently guaranteed. If a same-day missed prime will use immediate dispatch, also run `find_dispatch_collisions(plan, dispatch_time)` and report every future prime inside the temporary window, asking whether to prioritize the immediate best-effort or the future target. The normal 09:00/20:00 plan is not a collision.
- Resolve local work times explicitly: reject nonexistent spring-forward wall times; for ambiguous fall-back times use the earlier occurrence unless the v1 input supplies an explicit offset. Compute prime and collision gaps on the UTC timeline.
- Never read, print, copy, or include authentication files in prompts, commits, Issues, Pull Requests, or logs.
